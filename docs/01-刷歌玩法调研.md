# 「刷歌」玩法调研（动手写代码之前先把玩法吃透）

> 日期：2026-11-27 · 结论先行：**「刷歌」= 把抖音那套"全屏单页、竖向上滑、自动播放、无限推荐流"的交互，原封不动搬到音乐消费上。**
> 不是新发明，是交互范式的跨品类迁移。先搞清楚它为什么有效，再决定我们抄哪些、改哪些。

---

## 1. 它到底是什么

| 维度 | 传统音乐 App（歌单 / 榜单） | 刷歌模式 |
|---|---|---|
| 入口 | 先找 → 再听 | 打开就播，零决策 |
| 单位 | 歌单 / 专辑 | **一首歌 = 一屏** |
| 切歌 | 点下一首 / 列表选 | **上滑**（下滑回看历史） |
| 起播位置 | 0:00 | **直接跳高潮段**（约 15 秒预览，不喜欢立刻划走） |
| 反馈 | 显式收藏 / 评分 | **隐式行为**：完播、跳过时机、重复播放、双击红心 |
| 视觉 | 封面 + 进度条 | 全屏动态封面 / MV 片段 + **实时滚动歌词** |
| 内容形态 | 纯音频 | 音频流里**穿插音乐短视频**（翻唱、live、舞蹈剪辑） |
| 商业 | 会员 | **免费 + 看广告换时长**（看 15 秒广告 → 免费听 30 分钟）+ 会员 |

### 来源拆解（谁先做的、QQ 音乐怎么跟的）

- **汽水音乐（字节）**：这个玩法的原型。产品分析普遍描述为"打开直接播系统推荐的歌，上滑切歌，和刷抖音操作一致；过程中穿插音乐短视频推歌"；"每首歌自动播 15 秒左右的高潮段，不喜欢上滑换下一首，喜欢就停下来听完"；"上滑切歌 + 双击收藏，每首歌配动态封面和实时歌词；可回听历史"。
- **QQ 音乐**：
  - 「雷达模式」（V11.8.1 起）：按用户红心偏好生成，20 首一组，页面**上滑**可关联该歌的 MV / live / 综艺视频——这是 QQ 音乐内最早的"竖滑听歌流"雏形。
  - 「免费听歌模式」：观看 15 秒广告换 30 分钟免费听 VIP 歌曲，页面内是个性化 VIP 歌曲推荐流。
  - 海外报道（RouteNote）明确提到：面对汽水音乐"Swipe to Listen"的压力，腾讯在自家产品中加入了同款滑动式音乐发现流。
  - ⚠️ 诚实声明：**我没找到腾讯官方把这个入口正式命名为「刷歌」的公告**。公开检索到的 QQ 音乐版本日志（13.x → 20.x）里对应的词是「雷达」「免费听歌模式」「全新发现页」。「刷歌」大概率是用户/业界对这类竖滑听歌流的统称，或是 App 内 tab 文案。如果你手机上就叫「刷歌」，以 App 为准，玩法内核是一致的。

## 2. 第一性原理：为什么这玩法成立

1. **决策成本 → 0**。歌单模式要用户先回答"我想听什么"，刷歌模式把问题换成"这首行不行"——二选一比开放题便宜一个量级。
2. **信息密度最大化**。从高潮段起播，15 秒内给出一首歌最有辨识度的部分。人对一首歌的"喜欢/不喜欢"判断本来就只需要几秒。
3. **隐式反馈 > 显式标签**。"前 15 秒划走"和"听到 2:30 划走"是完全不同的信号；一周内重复播 3 次以上算强正反馈。用户不用打标签，行为就是标签。
4. **无限流 = 停留时长**。没有"列表到底了"这个退出点。这是抖音验证过的留存机器。
5. **低成本的内容飞轮**。短视频平台已经训练了十亿人的拇指；汽水从抖音导流（约 80% 流量来自抖音生态），QQ 音乐则靠自己的曲库 + 雷达偏好数据跟进。

---

## 3. 该怀疑的地方（别光抄）

- **过滤气泡 + 热歌偏置**：算法围着热歌转，小众老歌、欧美经典专辑容易被埋。多篇评测都指出汽水"发现新歌强、曲库深度和社区氛围弱"。
- **自动换歌的体验坑**：QQ 音乐自己的 PRD 复盘里就提过"滑动页面自动替换正在播放的音乐，用户可能不希望这样"。**后台/锁屏播放时的滑动语义要想清楚**。
- **15 秒预览 vs 完整听感**：高潮段起播适合"筛"，但会误伤慢热型歌曲（前奏长的后摇、古典、氛围音乐基本直接死）。
- **版权**：这是真正的护城河，不是交互。个人项目先用免费/合法音源，别碰灰色 API。
- **第三方下载站数据**（月活、命中率 97% 之类）一律不可信，本文未采用。

## 4. 功能拆解 → MVP 范围

### 必做（P0，没有就不叫刷歌）
- 全屏单页卡片流，竖向 Pager，上滑下一首、下滑回上一首（可回看历史）
- 自动播放；滑到即播，离开即停；**起播点 = 高潮段时间戳**（没有标注时退化为 30% 位置）
- 动态封面（放大 + 缓慢漂移/模糊背景）+ 实时滚动歌词
- 双击红心；右侧操作栏：红心 / 评论 / 分享 / 加歌单 / "不感兴趣"
- 底部：歌名、歌手、进度条（可拖动）、播放/暂停

### 应做（P1）
- 隐式反馈埋点：完播率、跳过时间点、重复播放、红心、分享 → 本地权重
- 简单推荐：基于标签/歌手/BPM 的相似度 + 探索比例（例如 80% 相似 / 20% 探索，避免气泡）
- "刷到视频"：流里按比例穿插 MV / live 片段卡
- 预加载下一首（音频 + 封面），滑动零等待

### 可做（P2）
- 看广告换时长的免费模式（纯 UI 模拟）
- 雷达式"20 首一组"的会话结构 + 组末总结卡
- 一起听 / 分享卡片

## 5. 技术方案建议（待你拍板）

| 选项 | 优点 | 代价 |
|---|---|---|
| **Flutter**（推荐） | 一套代码 iOS/Android，PageView 竖滑 + 音频库成熟（just_audio / audio_service），锁屏/后台播放好做 | 需要 Dart |
| React Native / Expo | JS 生态，expo-av 可用 | 后台音频和手势性能略逊 |
| Web PWA（Next.js/Vite） | 零安装、本容器可直接跑起来预览 | 移动端后台播放受浏览器限制，手势体感差一些 |
| 原生 Swift / Kotlin | 体验最好 | 单平台，开发量 ×2 |

**音源建议**：开发期用 iTunes Search API 的 30 秒预览（免费、合法、自带高潮片段）或 Jamendo / Free Music Archive；数据层抽象成 `TrackSource` 接口，后续换真实曲库零成本。

## 6. 已拍板的决策（2026-11-27）

| 问题 | 决定 | 理由 |
|---|---|---|
| 技术栈 | **Flutter** | 一套代码覆盖 iOS 和安卓，竖滑翻页与后台音频生态成熟 |
| 音源 | **iTunes 30 秒试听** | 免费合法，片段本身接近高潮段，天然契合「刷」 |
| 范围 | **纯前端 Demo** | P0 交互全做；推荐与埋点放在本机 |

实现与调研的差异：

- 「刷到视频」（流中穿插 MV）和「看广告换时长」属于 P1/P2，本版未做。
- 评论改为「心得」，只存本机，界面明确提示不上传，避免假装有社区。
- 新增「我的口味画像」弹层，把推荐依据摊开给用户看，可一键重置。
